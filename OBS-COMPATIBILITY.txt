OBS 配置推荐（可选客户端） / Recommended OBS settings (optional client)
================================================
项目版本 / Project version: v1.35

中文
----

本文件仅提供选择 OBS 时的配置推荐。项目也接受符合协议、编码及认证要求的其他推流客户端。

发布地址与来源
<LAN_IP> 是服务器监听推流流量的私网 IPv4，不是 PUBLIC_DOMAIN。WHIP TCP/8889
和 RTMP TCP/1935 仅绑定该地址；发布同时检查密码、所选接口真实局域网段及本机
/32。WHIP_IP 留空时优先自动选择默认路由的已启用 RFC1918 网卡，多网卡时可
指定某个本机私网地址。INGEST_ALLOW_CIDRS 手工值不会扩大范围；在防火墙中
另行放行一个 VPN 地址池也不会绕过程序来源检查。检查依据服务器实际看到的
源 IP；NAT/代理改写成获准地址会掩盖原始来源，因此不要向公网转发 8889/1935。

自动选择配置示例（部署前仍须检查包内 config.env 的现有值）：
  WHIP_IP=
  INGEST_ALLOW_CIDRS=

推流码由启动过程生成。systemd 模式启动后使用 sudo ./show-credentials.sh 查看；
手工模式会显示推流码。若已有持久凭据，两种模式都会复用；全新手工启动生成的
当次推流码不持久化。普通停止/重启不主动轮换已有持久凭据。

WHIP
  Service:       WHIP
  Server:        http://<LAN_IP>:8889/live/whip
  Bearer Token:  obs:<随机推流码>

本项目的 WebRTC 轨道收集期限是 15 秒，允许软件编码器较慢的初始化。
HTTP WHIP 信令及其中的凭据是明文，仅用于所选可信局域网；媒体通过 UDP/TCP
8189 的 DTLS-SRTP 加密通道传输。公网播放域名不作为推流入口。

建议先使用单路视频、整数帧率和明确的关键帧间隔：
  帧率：24/25/30/50/60 FPS 等
  关键帧间隔：1～2 秒
  服务端：目标 2 秒媒体段、1 秒 CMAF part，保留 24 段

1 秒 part 对这些帧率为整帧周期；实际段长仍依赖关键帧和时间戳。

x264：
  Rate Control       CBR
  Keyframe Interval  1～2 秒
  CPU Usage Preset   veryfast 或更快，先确保实时编码
  Profile            main 或 baseline
  Tune               zerolatency
  B-frames           0
  Repeat Headers     enabled

H.264 B 帧不适用于浏览器 WebRTC。OBS 的 WHIP 服务会向编码器请求 bf=0 和
repeat_headers=true，但应确认高级选项没有覆盖这些设置。
  [OBS WHIP 服务源码](https://github.com/obsproject/obs-studio/blob/master/plugins/obs-webrtc/whip-service.cpp)

SVT-AV1：
  Rate Control       CBR
  Keyframe Interval  1～2 秒
  Format             8-bit 4:2:0
  Preset             从能保持实时的较快档位开始

OBS 的 AV1 封装在 CBR 路径为 SVT-AV1 设置 low-delay 预测结构。CQP/VBR 不沿用
该设置，可能产生不适合 WHIP 的帧重排；应核对所用 OBS/编码器日志与高级选项。
  [OBS AV1 编码器源码](https://github.com/obsproject/obs-studio/blob/master/plugins/obs-ffmpeg/obs-ffmpeg-av1.c)

AOM AV1：
  Rate Control       CBR
  Keyframe Interval  1～2 秒，不能使用 0/自动
  Format             8-bit 4:2:0
  CPU Usage          realtime，或能保持实时的设置

这些参数是兼容性起点，不会让不支持该编码的浏览器获得解码能力。

RTMP 兼容入口
WHIP 下仍断流或输入存在不适合 WebRTC 的重排时，可独立测试 RTMP：
  Service:     Custom / 自定义
  Server:      rtmp://<LAN_IP>:1935
  Stream key:  live?user=obs&pass=<随机推流码>

pass 前不要再添加 obs:。完整地址形如：
  rtmp://<LAN_IP>:1935/live?user=obs&pass=<随机推流码>

RTMP 是明文协议，仅限程序检测的可信发布范围。RTMP 能接收重排/时间戳结构，
但不保证相同流经 WHEP 输出后仍可播放；必要时用 LL-HLS 单独验证。
随附 MediaMTX v1.21.0-r11 和 gortmplib v1.0.2 修补会忽略 AOM AV1 的空 Enhanced
RTMP sequence-start，等待后续有效 av1C。start.sh 使用随附修补二进制，不会下载
官方二进制替换它。

诊断断流
先检查日志和实时编码是否跟得上；可用 1920x1080、30 FPS 和较快 preset 缩小范围。
OBS 日志若出现：
  Encoding queue duration surpassed 5 seconds, terminating encoder
表示 OBS 因编码队列超时主动终止编码器，应根据实际负载调整编码设置；
它不表示 MediaMTX 因密码或来源检查而拒绝连接。

AOM AV1 有流但无画面
1. 关键帧间隔必须明确为 1～2 秒。若日志出现
   muxer error: reached maximum segment size
   且 HLS 清单失败，应检查长期缺少随机访问帧等导致分段超限的原因；
   设置 2 秒后重新推流验证，不能只凭 HTTP 状态就断定唯一根因。
2. MediaMTX 归一化 AV1 OBU，且仅在真实 KEY_FRAME 缺序列头时补回缓存配置；
   服务器不转码。
3. AUTO 有 RTCPeerConnection 时先尝试 WHEP，无 WebRTC 时走 HLS。HLS 主清单
   只作为并行能力提示，不阻塞 WHEP；手动 LL-HLS 和手动 WHEP 可分别诊断。
4. WHEP 建立期限 15 秒。手动超时/不支持时保留选择并允许重试，AUTO 有受控
   重试与回退；手动 LL-HLS 保留清单重试。
5. 浏览器必须声明相应的 AV1/90000 或 VP9/90000 WebRTC 能力，且能实际解码。
   公网 WHEP 信令是 https://<PUBLIC_DOMAIN>[:PUBLIC_HTTPS_PORT]/rtc/live/whep；
   UDP/8189 媒体优先，TCP/8189 回退。PUBLIC_HOST/NAT 要求见 DNS-SETUP.txt。
6. WHEP 连接后 18 秒仍无可显示画面，播放器区分“未收到 RTP”和“收到 RTP
   但解码帧为 0”，分别提示网络路径或编码兼容问题。RTP 持续增长也不能单独
   证明持续解码成功；需观察实际帧和播放时间。
7. 浏览器无对应解码能力时，应换兼容客户端或在 OBS 选择兼容编码，例如 H.264。

WHEP 无声音
1. 网页初始静音，点击“开启声音”。
2. WHIP 使用 Opus；播放器把分开到达的视频/音频轨合并到同一个 MediaStream，
   并显式协商 Opus stereo/sprop-stereo。
3. RTMP 常用 AAC，WHEP 不支持 AAC。需要声音时切到兼容的 LL-HLS，或用
   WHIP 发送 Opus；服务器不会自动做 AAC -> Opus 转换。
4. 缺少音轨时按网页提示检查 OBS 音轨启用、静音和输入状态。
   [MediaMTX WebRTC 播放](https://mediamtx.org/docs/read/webrtc)

LL-HLS 弱网模式
Normal 目标延迟 6 秒、最大播放速率 1.05x；Weak 目标 12 秒、速率 1.00x。
bandwidth-loss 保留低延迟 parts；RTT Weak 改用整段。Weak 实际连续前向缓冲
首次达到 8 秒才 READY，低于 6 秒时在监测采样中取消 READY。播放器的目标和
缓冲策略不会修改 OBS 编码参数、转码或保证任意带宽/断网条件下不停播。
SourceBuffer append 归属保护、网络错误触发及恢复条件完整说明见 CODEC-SUPPORT.txt。

English
-------

This guide provides recommended settings when using OBS. Other publishing clients
that meet the protocol, codec and authentication requirements are also supported.

Publishing address and sources
<LAN_IP> is the server's private IPv4 publishing listener, not PUBLIC_DOMAIN. WHIP
TCP/8889 and RTMP TCP/1935 bind only there. Publishing checks the password and the
selected interface's actual LAN subnet plus the server /32 address. An empty
WHIP_IP prefers an active RFC1918 interface associated with the default route;
set a local private address explicitly on multihomed servers. Manual
INGEST_ALLOW_CIDRS values do not expand access. Allowing another VPN pool in the
firewall does not bypass the application's source check. Checks use the source
IP seen by the server; NAT/proxy rewriting to an approved address can hide the
original origin, so never forward 8889/1935 publicly.

Automatic-selection example (review the package's existing config.env first):
  WHIP_IP=
  INGEST_ALLOW_CIDRS=

Startup generates the stream key. After systemd startup, use
sudo ./show-credentials.sh to view it; manual startup prints it. Both modes reuse
existing persisted credentials. A fresh manual run does not persist its temporary
stream key. Normal stop/restart does not rotate existing persisted credentials.

WHIP
  Service:       WHIP
  Server:        http://<LAN_IP>:8889/live/whip
  Bearer Token:  obs:<random-stream-key>

The project's WebRTC track-gather deadline is 15 seconds, allowing slower encoder
initialization. HTTP WHIP signalling and its credentials are plaintext and belong
only on the selected trusted LAN. Media uses DTLS-SRTP on UDP/TCP 8189. The public
viewer hostname is not a publishing endpoint.

Start with one video stream, an integer frame rate and an explicit keyframe interval:
  Frame rate:         24/25/30/50/60 FPS, for example
  Keyframe interval:  1–2 seconds
  Server:             2-second segment target, 1-second CMAF parts, 24 segments

One-second parts align with complete frame periods at these frame rates; actual
segment lengths still depend on keyframes and timestamps.

x264:
  Rate Control       CBR
  Keyframe Interval  1–2 seconds
  CPU Usage Preset   veryfast or faster; establish real-time encoding first
  Profile            main or baseline
  Tune               zerolatency
  B-frames           0
  Repeat Headers     enabled

Browser WebRTC does not support H.264 B-frames. OBS's WHIP service requests bf=0
and repeat_headers=true; check that advanced settings do not override them.
  [OBS WHIP service source](https://github.com/obsproject/obs-studio/blob/master/plugins/obs-webrtc/whip-service.cpp)

SVT-AV1:
  Rate Control       CBR
  Keyframe Interval  1–2 seconds
  Format             8-bit 4:2:0
  Preset             Start with a faster setting that maintains real time

OBS's AV1 wrapper sets the SVT-AV1 low-delay prediction structure in the CBR path.
CQP/VBR do not use that setting and may produce reordering unsuitable for WHIP.
Check your actual OBS/encoder logs and advanced options.
  [OBS AV1 encoder source](https://github.com/obsproject/obs-studio/blob/master/plugins/obs-ffmpeg/obs-ffmpeg-av1.c)

AOM AV1:
  Rate Control       CBR
  Keyframe Interval  1–2 seconds, never 0/automatic
  Format             8-bit 4:2:0
  CPU Usage          realtime, or a setting that maintains real time

These settings are compatibility starting points; they do not add codec support
to a browser that lacks it.

RTMP compatibility input
If WHIP disconnects or the input has reordering unsuitable for WebRTC, test RTMP
independently:
  Service:     Custom
  Server:      rtmp://<LAN_IP>:1935
  Stream key:  live?user=obs&pass=<random-stream-key>

Do not prepend obs: to pass. The complete URL is:
  rtmp://<LAN_IP>:1935/live?user=obs&pass=<random-stream-key>

RTMP is plaintext and restricted to the detected trusted publishing range. It can
accept reordering/timestamp structures, but that does not guarantee the same
stream works through WHEP. Test LL-HLS separately when needed. The bundled
MediaMTX v1.21.0-r11 and gortmplib v1.0.2 patch ignore an empty AOM AV1 Enhanced
RTMP sequence-start and wait for valid av1C. start.sh uses the bundled patched
binary and does not download an official binary over it.

Diagnosing disconnects
Check logs and real-time encoding throughput. A 1920x1080, 30 FPS test with a faster
preset can narrow the cause. This OBS log entry:
  Encoding queue duration surpassed 5 seconds, terminating encoder
means OBS terminated the encoder because its queue timed out. Adjust settings
according to measured load; this message does not mean MediaMTX rejected the
password or source address.

AOM AV1 arrives but there is no picture
1. Set an explicit 1–2-second keyframe interval. If logs report
   muxer error: reached maximum segment size
   and HLS playlists fail, investigate causes such as missing random-access
   frames that prevent segmentation. Retest after setting 2 seconds; an HTTP
   status alone does not establish a unique cause.
2. MediaMTX normalizes AV1 OBUs and restores a cached sequence header only when
   a real KEY_FRAME lacks it. The server does not transcode.
3. AUTO tries WHEP first when RTCPeerConnection exists and HLS otherwise. HLS
   master metadata is only a parallel hint; it does not block WHEP. Use manual
   LL-HLS and manual WHEP to diagnose each path independently.
4. WHEP has a 15-second connection deadline. Manual timeout/codec failure keeps
   the selected mode and permits retry. AUTO has controlled retries/fallback;
   manual LL-HLS retains playlist retries.
5. The browser must advertise AV1/90000 or VP9/90000, as applicable, and actually
   decode the stream. Public WHEP signalling uses
   https://<PUBLIC_DOMAIN>[:PUBLIC_HTTPS_PORT]/rtc/live/whep;
   UDP/8189 media is preferred, with TCP/8189 fallback. See DNS-SETUP.txt for
   PUBLIC_HOST and NAT requirements.
6. If no displayable frame appears within 18 seconds after WHEP connects, the
   player distinguishes no received RTP from received RTP with zero decoded
   frames, guiding network or codec diagnosis. Increasing RTP counters alone
   do not prove continuous decoding; observe frames and playback time.
7. If the browser lacks the decoder, use a compatible client or choose a
   compatible OBS codec such as H.264.

WHEP has no sound
1. The page starts muted; click its sound button.
2. WHIP uses Opus. The player combines separately arriving video/audio tracks
   into one MediaStream and explicitly negotiates Opus stereo/sprop-stereo.
3. RTMP commonly uses AAC, which WHEP does not support. Use compatible LL-HLS
   playback for sound, or publish Opus through WHIP. The server does not convert
   AAC to Opus.
4. For missing audio tracks, follow the page's message and check OBS track
   enablement, mute state and audio inputs.
   [MediaMTX WebRTC playback](https://mediamtx.org/docs/read/webrtc)

LL-HLS weak-network mode
Normal targets 6 seconds of latency with a maximum 1.05x playback rate; Weak
targets 12 seconds at 1.00x. bandwidth-loss retains low-latency parts; RTT Weak
uses full segments. Weak first becomes READY at 8 seconds of actual continuous
forward buffer; a monitoring sample below 6 seconds clears readiness. These
player targets and buffer policies do not alter OBS encoding, transcode or
guarantee uninterrupted playback through arbitrary bandwidth limits/outages.
See CODEC-SUPPORT.txt for append ownership, network-error protection and recovery
conditions.
